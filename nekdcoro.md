# Naked Coroutines

*An immediate-mode TUI paradigm built on structured concurrency.*

> Parent composes seams; children draw into themselves.

Most UI frameworks assume a separation between a program and its presentation. The program holds state; a presentation layer reads that state and renders it. Widgets are objects with their own lifecycles, managed by the framework, holding references to the data they display. The two layers communicate via callbacks, observers, signal/slot wiring, or data binding. The separation is so reflexive that it's hard to notice it being a choice.

This document describes a different commitment, made possible by structured concurrency together with immediate-mode rendering, and adopted in the TUI layer of the `nxt` runtime. The commitment is: there is no presentation layer. There are coroutines doing work, and each coroutine that wants to be visible draws into a *seam* — a small framed surface along which its current rendering becomes available to whatever parent composes it. The drawing is a value, produced on demand from the coroutine's current state, replaced wholesale on each redraw. The visible structure of the program is the structure of the coroutine tree, made geometric.

We call this *naked coroutines*, after Pawson's naked objects from a quarter century ago. The agreement and disagreement with that earlier proposal are both instructive, and we'll come back to them.

## Seams

A *seam* is where two regions of the runtime meet. On one side is a coroutine drawing from its own interior — its locals, its accumulated state, its work in progress. On the other side is a parent composing that drawing into a larger arrangement. The seam doesn't carry data through; it doesn't expose the child's internals; it exposes only the rectangle the child has most recently drawn, framed for the parent to place. Christopher Alexander's *Zen View* pattern captures the spirit: a small humble window onto a durable world, with the view changing as the world changes, but the world remaining its own thing on the other side of the frame.

A seam is born when a child coroutine is spawned, and it closes when that child ends. There is no way to construct a seam outside of spawning a coroutine; the runtime makes them, the way it makes deeds and zones, and hands them out as part of the structured-concurrency machinery. A parent receives no special object to "register a child"; the child is forked, the seam comes into being attached to the deed, and the parent's composition can enumerate the seams of its currently-live children directly from the zone.

When the coroutine's state changes in a way that should be visible, it calls `draw(layout)` — where `layout` is a fresh value computed from current locals. The seam's content is replaced. The framework's render pump composes whatever's currently across each seam at frame rate, and re-renders the existing contents when the terminal resizes. Between `draw` calls, nothing is happening: no widget tree being mutated, no observers firing, no diffing. The drawing sits at the seam until the producing coroutine sends a new one or the seam closes.

The layout itself is a value type, not a tree of objects. A static-shape composition like `row(a, b, c)` produces a concrete `Row<A, B, C>` that lives on the stack inside the seam, with its children as direct members. A homogeneous list of items doesn't materialize per-item layouts at all: a combinator like `list(span<T>, view_fn)` holds a reference to a range and a view function, and child layouts are constructed transiently at render time and dropped immediately. The pattern that emerges is: no retained widget tree, no shared ownership of subtrees, no mutable widget state. State lives in coroutines; layouts are functions over state, evaluated when the screen needs to know what the state currently looks like.

This makes resize and state change orthogonal. A resize is the framework's problem: re-render existing seam contents at a new size, using the layout values that are already there. A state change is the coroutine's problem: call `draw` again with new content. A long-quiet coroutine doesn't need to redraw when the terminal resizes, because its existing layout will respond to the new geometry on its own. A coroutine producing state changes in a stable-size terminal doesn't need the framework to recompute layout from scratch.

## Why it's safe

Layouts that reference state living somewhere else are dangerous in general. Most immediate-mode systems handle the danger by materializing — every draw call produces a self-contained owned layout that copies what it needs, so nothing in the layout outlives the call. That works, but it's expensive: every draw allocates, every redraw copies, the per-frame cost scales with the depth and breadth of the displayed structure.

Structured concurrency makes the safe version cheap, *if* seams are not free-floating. The invariant the runtime enforces is: a seam is a child resource of a deed. It is born when the child is forked, and it is unregistered when the deed completes — and unregistration happens *before* the coroutine frame is allowed to be destroyed. The window in which a parent could compose a seam after its frame is gone does not exist. The structural guarantee about parent-joining-child translates directly into a lifetime guarantee about seam contents.

This lets the layout layer be lazy in the way it wants to be. A drawing across a seam can hold a `span<const T>` pointing into the producing coroutine's local vector. It can close over a reference to a string the coroutine is still mutating. It can refer to anything the coroutine's frame holds, because the seam exists only while the frame exists, and the seam closes before the frame goes. The borrow-checker-shaped question — *what if the data is gone when the renderer fires* — is answered by the runtime's ordering of cleanup. The data is never gone while the seam is open.

This is the same trick RAII pulls for resources, extended one more domain. Files close when their owning scope ends. Sockets close. Cgroups detach. Trace spans finalize. Seams close too — visibility becomes a kind of resource, owned by a scope, released when the scope ends. The lifetime that would otherwise dog any lazy-view design is closed by construction: the view and the data have the same death.

## Composition and the geometric envelope

When a coroutine has children — forked into the same structured-concurrency zone — those children own their own seams. The parent's job is to compose its children's seams into its own drawing. A column composition stacks them vertically. A row composition arranges them side by side. A metering composition adds chrome around the child arrangement: a top bar, a side panel, a status footer.

The chrome lives where it belongs, in the parent. A parent that wants to display "tasks running, bytes transferred, time elapsed" has those facts because it spawned the children and observes them. There is no separate stats widget reading from a shared model; the stats are local to the parent, derived from the parent's own knowledge of what it spawned, and painted by the parent into its own drawing — which it composes alongside the seams of its children.

This gives the screen's geometric arrangement a structural meaning. A top bar above a working area above a footer is a parent contributing chrome around a child seam. Geometric containment is structural containment. The screen tells the truth about the tree.

The same insight shapes how seams are addressed. The runtime already lets you find the current zone via dynamic lookup — `fork(child)` finds the enclosing zone in an environment binding, rather than requiring you to thread the zone through every signature. The current drawing seam can work the same way. `draw(layout)` finds the current seam from the environment; entering a child scope rebinds it. Composition helpers like `with_top_bar(make_bar, body)` create a child seam, install a parent redraw that puts `make_bar()` above the child's drawing, and run the body in the child's context. The structural tree, the layout tree, and the environment-binding stack all line up. There is no separate scope object that has to be carried around — the seam is wherever the dynamic context says it is, and the geometric arrangement falls out of how that context nests.

`accompany` and similar helpers stop being primitives in this view. They become consequences: a `fork` of a worker, a `fork` of a companion, and a parent draw that composes their seams via a supplied function. The n=2 special case loses its specialness. The general form — read the live seams from the current zone and arrange them — covers everything; `accompany` is just that with a fixed compose function and exactly two children. The API surface shrinks because the primitive moved underneath it.

## Data and processes

A common pattern: a coroutine accumulates information over time — log lines arriving on a channel, search hits being parsed, sensor readings being sampled. The coroutine holds the information in its frame — a ring buffer, a vector, a deque — and on each update calls `draw` with a layout that reads from it. The data lives where the computation lives. There is no separate "log widget" holding the buffer; there is the log-tailing coroutine, which both reads lines and shows them.

A different pattern: a coroutine spawns N child coroutines, each doing its own work — a batch of tool calls executing concurrently, several builds running in parallel, multiple network requests in flight. The children are not data. They are running computations with their own observable state, their own resource use, their own ends. The parent does not hold a vector of child-records to render. The parent has N children in its zone, each with its own seam, each drawing its own surface; the parent's draw composes those seams.

The distinction matters because it determines where state lives. Passive records, parsed events, accumulated history — these live in the locals of the coroutine that processes them, displayed by a lazy view combinator over the source data. Running entities with lifecycles — these live as forked children, with their visible presence equal to their structural presence. The error to avoid is treating processes as data. A tool batch executing N tool calls is not the agent's vector of call-records to be rendered; it is N coroutines doing tool work, each with its own progress, each with its own end. Modeling them as data flattens out their structure: you lose the ability to compose chrome around individual ones, to cancel them individually, to have their visual presence end when their work ends. The fix is to let processes be processes — fork them as children, let them own their seams, let the parent compose.

A consequence worth naming: when the question is "should I hold a vector here," the answer is governed by what kind of thing the vector contains. A vector of data — log lines, parsed records, accumulated samples — belongs in a coroutine's locals, displayed by a lazy combinator that reads it. A vector of running things — tool calls, requests, builds — does not belong anywhere; the things should be children, and the runtime keeps track of them. The instinct to put pre-materialized child layouts into a vector of type-erased layouts is almost always a misclassification.

## Lazy views, range adaptors

If the layout is a value computed on demand from current state, and the data is already in some range-shaped structure the coroutine maintains, then the right way to thread data into rendering is through ranges. A lazy combinator like `each(range, view_fn)` consumes any input range — a vector, a span, a `views::filter` result, a `views::take` result — and constructs child layouts transiently as it iterates. The composition chain `buffer | drop(scroll_offset) | take(viewport_rows) | each_into(render_line)` says exactly what a scrolling log pane wants to say: take a slice of the buffer at the current scroll position, give one rendered row per item, materialize nothing in between.

This is the data-layer analog of "layouts are produced on demand": the pipeline computes the visible slice each draw, never copies, never holds an intermediate. The structural commitment underneath ranges and the structural commitment underneath naked coroutines are the same — don't keep intermediate objects around, express transformations as functions over source data, materialize only what's being looked at right now. The two layers compose naturally: a coroutine's local data flows through range adaptors into render combinators, with no materialization anywhere along the path. The lifetime story makes it safe; ranges make it expressive.

## Naked objects, twenty-five years on

Pawson's *Naked Objects* argued that business applications should be built from domain objects directly visible and directly manipulable, with no separate presentation layer. The thesis was epistemic and structural: a presentation layer is a translation layer, and translation layers accumulate slop, drift from the model they translate, and become where bugs and design debt collect. Make the objects naked — let users manipulate them directly — and the slop has nowhere to live.

The agreement with naked coroutines is the same underlying conviction: don't put a translation layer between the thing and its representation, because translation layers are where dishonesty becomes possible. Let the structure of the thing be what's shown.

The disagreement is what counts as the unit. Naked objects assumed the world was made of nouns — customers, orders, accounts — entities sitting still and waited on. A great deal of modern software is not well-modeled as nouns. It is made of verbs: tool calls in flight, network requests pending, pipelines running, agents acting. Verbs reified as nouns are procrustean; they don't have lifecycles in the way running computations do, they don't end, they sit still in a way that processes don't. Naked coroutines fixes the ontology. The unit is a structured live thing with a beginning and an end, with parents and children, with observable state evolving in time. The screen shows the verb tree.

The substrate also gives naked coroutines something naked objects couldn't quite have: compositional UI without a layout engine doing inference. Naked objects had to derive a UI from object structure — fields became inputs, methods became buttons, types became widgets — and the derivation was always a heuristic, working better for some objects than others, requiring annotation and override for anything complex. Naked coroutines doesn't need a derivation. The coroutine draws what it draws; child coroutines have their own seams; the parent composes. There is no presentation logic to generate, because there is no presentation layer at all — there is the coroutine, the seam, and whatever the coroutine drew across it. The presentation hasn't been generated; it's been removed.

This is, in a sense, more deeply naked than naked objects. Naked objects exposed nouns through a UI generator. Naked coroutines exposes verbs by removing the generator. There is nothing between the running computation and its visible surface: the running computation produces the surface itself, and the surface ends when the computation ends.

## What this offers

What this paradigm offers, in the end, is honesty. The screen shows what is happening. Chrome positions correspond to parent-child relations. The presence of a drawing corresponds to the aliveness of a coroutine. Aggregate stats live with the scope that aggregates them. There is no separate model of the world that the UI is curating — the UI is a window onto the world the runtime maintains. The thing on screen is the system, made visible.

When the foundation is logical, design becomes derivable. Choices that would otherwise be aesthetic — where does the metering go, when does this disappear, how does this compose with that — become structural. Where the metering goes is determined by which scope is observing what; when something disappears is determined by when its coroutine ends; how things compose is determined by which scope contains which. The UI inherits the discipline of the runtime, because they are the same structure expressed in different substrates. Doing the architectural work is doing the design work. The system being well-structured and the UI being well-designed collapse into the same condition.

The mechanics are small. Seams are how a coroutine's drawing becomes available to its parent's composition, born with the child and closing when the child ends. Layouts are values computed on demand, never retained. Composition happens at the parent, alongside whatever chrome the parent contributes from its own knowledge. Lazy combinators thread data through views without materialization. Structured concurrency closes the lifetime questions before they become problems.

The consequences are not small: a paradigm in which running programs render themselves, in which the screen tells the truth, in which UI design becomes a corollary of system design rather than a separate craft. *Parent composes seams; children draw into themselves.* The runtime is already shaped for it. Most of what remains is letting that shape come through.
